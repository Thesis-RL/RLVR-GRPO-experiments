# LoRA gradient-direction audit protocol

The audit protocol was frozen on 23 November 2026 before calculating gradient
metrics. It uses saved training groups from three points in training.

## Audit inputs

- `priority_bridge_v2`, training seeds 0, 1, and 2.
- Six conditions pairing clean, FP-only, and FN-only verification with binary
  or fractional reward.
- Checkpoints at steps 112 (early), 561 (middle), and 1010 (late).
- At each checkpoint, the single group with the matching `policy_step` in
  `rollouts.jsonl`, containing 16 saved completions.
- A total of 6 × 3 × 3 = 54 checkpoint–group pairs.

Step 112 is the first saved checkpoint, 561 is the midpoint, and 1010 is the
last saved checkpoint with a training group generated by that policy.
Training ends at step 1122, so there is no subsequent group for that
checkpoint.

## Calculation

The audit uses each group's saved prompt, completions, clean and noisy rewards,
and advantages. It reuses the saved verifier results and completions.

1. Load the matching LoRA checkpoint on top of the pinned base model.
2. Run in `eval` mode to disable dropout during the clean–noisy comparison.
3. For each completion, differentiate the sum of token log probabilities
   with respect to the trainable LoRA parameters.
4. Linearly combine these gradients using the clean and noisy GRPO advantages.
   As in on-policy DAPO, divide the sum over completion tokens by the total
   number of completion tokens in the group.
5. Record the diagnostic metrics. The optimizer is left untouched, and the
   archive contains metrics derived from the gradients.

### Recovering token IDs

Rollout logs contain the decoded completion and `completion_token_count`.
The initial audit smoke run identified the absence of the original token
IDs before producing the aggregate results. Audit v1.1 uses a deterministic
reconstruction:

- Tokenize the visible text with the pinned tokenizer.
- Where the logged count exceeds the canonical visible count, restore one
  EOS/padding token. The Hugging Face generation path stopped at the first EOS.
- Count any remaining non-canonical subtokens as unrecoverable and omit them.

The audit restored 807 EOS tokens. Three of the 864 completions each had one
unrecoverable non-canonical subtoken.

The importance ratio is fixed at 1. This matches the executed training path
with `num_iterations=1`, aligned gradient accumulation, and `use_vllm=false`.
The PPO/DAPO clipping rate is therefore zero by design and is recorded as a
protocol check.

Each checkpoint–group pair yields two comparisons:

- Binary clean gradient versus binary noisy gradient.
- Fractional clean gradient versus fractional noisy gradient.

The aggregation used during training is primary. The other aggregation
provides a pre-specified counterfactual on the same completions and checkpoint.

## Metrics

The primary metric is cosine similarity between clean and noisy LoRA loss
gradients for the aggregation used during training.

Secondary metrics include:

- Gradient dot product.
- Clean and noisy gradient norms and their noisy-to-clean ratio.
- Proportion of negative alignments among defined cosines.
- Proportion of zero-gradient groups under clean and noisy rewards.
- Advantage cosine and sign agreement.
- The same metrics for the counterfactual aggregation.
- Breakdowns by training phase and seed.

The clean conditions serve as positive controls. Clean and noisy rewards
coincide in those conditions, so each nonzero gradient pair should have a
cosine close to 1.

## Interpretation

The audit shows how changes in advantages affect LoRA gradient direction in
one pre-selected group per phase, training seed, and condition. That
sampling limits conclusions to the audited groups. A cosine is reported as
undefined if either gradient is zero. The audit is diagnostic and leaves
the frozen test endpoint analysis and hyperparameter selection unchanged.
